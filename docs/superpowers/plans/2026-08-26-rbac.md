# Roles and Project-Scoped Write (WP-G1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Revision 2**, after review by `codex-reviewer` and `vibe-reviewer`. The architecture and the seam survived unchanged. What changed: the piece ordering created a security regression (fixed by failing closed), the create path needed an anti-escalation assertion, the audit rule was promoted to an authorization invariant with a positive test matrix, and several places where an implementer was left to infer a mechanism are now specified.

**Goal:** Give invctl three roles — Administrator, Observer, Project owner — assigned inside the product and audited, where a project owner may write only the assets, services and circuits linked to their projects, and where reaching a write without an authorization decision is a compile error rather than a review finding.

**Architecture:** A `role` column on `app_user` plus a `user_project` assignment table. Enforcement moves one level below the handler: `SQLStore.write` / `writeSerializable` / `writeTx` stop taking a `domain.Actor` and take a `domain.Permit` — an interface with an unexported method, so no type outside `internal/domain` can implement one and no handler can forge one. The per-object half rides `tx.log`, which is already the single insertion point for `change_log` and already receives exactly the `(entityType, entityID)` pair a scope check needs; a permit that does not cover the row being logged fails the transaction with `domain.ErrForbidden`.

**Tech Stack:** Go 1.22+ stdlib, `net/http.ServeMux`, `html/template`, `jmoiron/sqlx` with hand-written SQL, `pressly/goose/v3`, `alexedwards/argon2id`, HTMX 2.x. **No new dependencies.**

**Spec:** `docs/rbac-design.md` — including **§3 as corrected** (Administrator sees costs implicitly; **Observer and project owner both see costs only if granted**) and **§10a**, which records that this product has *no user administration at all* — no routes, no templates, no store methods beyond lookup and upsert, and **no scrub**, despite nine comments describing how one would degrade. That is why the size grew.
**Surface map:** `.superpowers/sdd/wp-g1-surface-map.md`

## Global Constraints

From `CLAUDE.md`, `docs/AUDIT.md` and the spec. Violating one is a rejected task.

- **Placeholders are `?`.** Call `sqlx.Rebind`. Never `$1`.
- **Every query runs unmodified on SQLite and PostgreSQL.** No `inet`, `cidr`, native arrays, `ENUM`, `jsonb` in `WHERE`, `SERIAL`, `generate_series()`, `NOW()` as a default, `num_nonnulls()`, `RETURNING` on multi-row statements.
- **Booleans are `TRUE`/`FALSE` literals**, never `0`/`1`.
- **IDs are UUIDv7 TEXT generated in Go. Timestamps are RFC3339 UTC TEXT generated in Go.** Never by the database.
- **Enums are `TEXT` with `CHECK (col IN (...))`** plus a matching Go constant set.
- **Every mutation of declared state writes a `change_log` row in the same transaction.** This is now an **authorization invariant**, not only an audit rule — see "The audit rule is load-bearing" below.
- **Creates are `INSERT`-only and fail on conflict.** Never `ON CONFLICT DO UPDATE`, never upsert-shaped, on any path a project owner can reach. A create that quietly becomes an update is how an existing entity gets seized. See Task 14.
- **Soft delete only.** A user is deactivated, never deleted. An assignment is retired, not removed.
- **`change_log.actor` holds an opaque `app_user.id`,** never a username. Attribution is server-derived from the credential, never read from a payload.
- **Costs are an orthogonal grant, and narrowing them is a behaviour change.** Spec §3 as corrected: Administrator implicitly; Observer and project owner **only if granted**. One column (`app_user.can_see_costs`), one screen, one audited change — **do not build two mechanisms**. `auth.CanSeeCosts` returns `CanRead(user)` verbatim today, so **every reader sees costs in every existing deployment**; this narrows that. It goes in the release note, not into somebody's morning.
- **A permit is request-scoped and immutable.** It carries no transaction-scoped state, so nothing survives a rollback and nothing needs resetting on a retry. See "Permit lifetime" below.
- **A project owner creates inside a project, by URL.** `POST /projects/{id}/assets/new` and its siblings. `POST /assets` stays Administrator-only for the unowned case.
- **Migrations are byte-identical between `internal/store/migrations/sqlite/` and `internal/store/migrations/postgres/`.** `TestEveryDialectMigrationHasBothHalves` guards this.
- **Licence header on every new `.go`, `.sql`, `.html`, `.css`, `.js` file**, followed by a **blank line** before the package clause:
  ```go
  // invctl — infrastructure inventory
  // Copyright (C) 2026 Madalin Ignisca <hi@madalin.me>
  //
  // Licensed under the GNU Affero General Public License, version 3 only —
  // no later version applies. See LICENSE for the full text.
  //
  // SPDX-License-Identifier: AGPL-3.0-only
  ```
- **`internal/domain` keeps zero external dependencies.**
- **Validation failure is 422** with the form partial re-rendered. **Authorization failure is 403** — `domain.ErrForbidden` already maps to it in `handleStoreError`.
- **`make test` is the gate, not `go test ./...`** — the latter silently skips Postgres.
- **`make lint` is the lint gate**, not `gofmt && go vet && staticcheck`.
- Test names are full behaviour sentences. Assert **exact values**, never lengths or `contains`.
- **Every new test must be observed failing.** Each task names the exact mutation that turns it red.

## Approach, and why this seam

### The scope reduction

The surface map's counts are the headline and must not be re-derived. Of 145 literal `write(` call sites in `internal/web/routes.go`:

| Group | Count | Needs a per-object check? |
|---|---|---|
| Asset / service / circuit mutations | ~40 | **Yes** |
| Project mutations (incl. `POST /projects/{id}/assets`) | 14 | No — Administrator-only, spec §4 |
| Topology with no project relation | 47 | No — Administrator-only |
| Estate-wide config | 25 | No — Administrator-only, spec §4 |
| Import, bulk, six GETs in the write bucket | 16 | Import and bulk: yes, via the same mechanism |

Three entity types are project-linkable and nothing else carries `project_id` anywhere in any migration. **A plan that treats all 175 registered write patterns as needing work is wrong.** The 86 topology-and-config routes keep exactly the middleware they have and gain no code.

### The seam: `store.write` / `writeSerializable` / `writeTx`, object check in `tx.log`

**`middleware.RequireAdmin` cannot work** — it runs before the handler knows the entity (spec §6). It keeps its present job: an Observer is refused before a handler runs.

**`handlers.actor(r)` is rejected as the seam.** It is a *helper*, not a chokepoint — a new handler that never calls it still compiles. The map records 140 call sites against 175 write patterns and explicitly marks this **NOT VERIFIED**. And the import runner has no request at write time at all (`import_runner.go` captures the actor at submit and runs on `context.Background()`, deliberately), so a request-scoped mechanism cannot reach the single largest write in the product. Task 6 still runs the mechanical check — as a committed, reusable helper — because Task 10 needs its output.

**`store.write` / `writeSerializable` / `writeTx` is the seam.** 150 measured call sites in non-test store files (two of which are `store.go`'s own delegation, leaving **148 real write transactions**), every one already threading a `domain.Actor` in from its caller — verified: no store method mints a `SystemActor` internally. `boundary_source_test.go:173-175` already names these three as a set. Changing their second parameter from `domain.Actor` to `domain.Permit`:

- makes **every write transaction, present and future, unable to exist without an authorization decision attached** — a compile error at 148 sites and at the 149th nobody has written yet;
- needs no maintained route list, which is the failure mode spec §6 names;
- reaches the import runner, the LDAP upsert and the seeder, none of which has a request.

**The per-object half rides `tx.log`.** `writeTx` does not know the entity id — the store *method* does. But so does `tx.log(ctx, entityType, entityID, action, diff, batchID)`, the **only** `INSERT INTO change_log` in the codebase (`internal/store/store.go:110-112`, held by `TestChangeLogIsAppendOnly` and `TestNoAssembledWriteReachesChangeLog`), through which all 147 audit call sites funnel. One guard, one function, exactly the pair the check needs, inside the transaction so refusal rolls the mutation back. **No per-method work**, which is the difference between this and forty places to forget.

### The audit rule is load-bearing for security now

Because authorization rides `tx.log`, **"every declared mutation writes a `change_log` row" stops being an audit rule and becomes an authorization invariant.** A declared mutation that does not log is not merely an untraceable change — it is an *unauthorized* change that succeeded.

**Every existing boundary test is negative.** `TestObservedPathTouchesNoDeclaredTable` proves the observed path does *not* log. `TestOnlyTheObservedPathWritesTheObservedTables` proves other paths do *not* write observed tables. `TestNoAssembledWriteReachesChangeLog` proves nothing forges an entry. **None of them proves that a declared mutation DOES log.** Task 8 adds that positive matrix, and Task 18 records the fact in `docs/AUDIT.md` so a future reader who wants to relax the rule has to meet it first.

### Permit lifetime, stated because it was not

- **The permit is request-scoped.** One decision per request, minted at the top by the gate (Task 12), passed down. It is never cached across requests: a cached permission set is a stale permission set, and the failure is a revoked project owner who keeps writing.
- **It is immutable.** No mutable state, no transaction-scoped set, nothing to discard on rollback and nothing to rebuild on a retry.

  This was not the first design. An earlier revision let the store record ids it had minted inside a transaction, so that create-and-link could be distinguished from link-an-existing-entity at check time. It worked, and it was tested. It was replaced because a reviewer asked what happens to that state when a `SQLITE_BUSY` or SQLSTATE 40001 retry rebuilds the transaction — and **making a question unaskable is strictly better than answering it correctly.** The replacement is a routing decision (Task 14), not a permit feature.
- **The permit survives a retry unchanged**, because there is nothing in it that a transaction could have changed.

### Copying both halves of the `boundary_source_test.go` technique

1. **The compile barrier.** `domain.Permit` carries an unexported method, so nothing outside `internal/domain` can implement it, and `domain.Actor` does not satisfy it. The analogue of `*SQLStore` deliberately not satisfying `ObservedStore`.
2. **The width lock.** A reflection assertion that `Permit` has exactly the expected methods by name and count — so widening it fails even though it compiles.
3. **The minter budget.** An AST walk asserting the set of functions returning a `Permit` is exactly the named set, per-file with an exact count.
   **This is governance, not security, and the plan says so out loud.** Somebody can add a minter and update the budget in the same commit and the test stays green. What it buys is that the addition is *visible* — a reviewer sees a budget line change and knows to look. The countermeasure is social, so it is written down: the budget map carries a comment naming **the repository owner as the person whose sign-off an addition needs**, and stating that a new permit minter is a security-relevant change requiring `auth-reviewer`.
4. **The loud hole.** An unclassified `entityType` fails on sight, the way `dynamicTable` does — never defaults to allow, and never denies silently, because a silent denial looks like a bug and gets "fixed" by widening the allowlist.

## The security consequence of the ordering, and the ruling

After Piece 1 the `role` column exists and `CanWrite` consults it. A ProjectOwner could be assigned and would pass `RequireAdmin` — **but the object gate does not exist until Piece 3.** They could write anything. That is strictly worse than today, where a person is either fully administrative or fully read-only.

**`CanWrite(ProjectOwner)` returns FALSE until the object gate is live.** A project owner is treated as an Observer for writes throughout Pieces 1 and 2. Task 13 — a single commit, on its own, after the gate and its tests are green — flips it in one place.

Fail-closed, and it is what makes Piece 1 genuinely safe to ship alone. The role can be assigned, is audited, and shows in the UI as *pending* — the screen must say so (Task 5), or an administrator will assign a role, watch nothing happen, and file a bug.

type Permit interface {

### Task 14: Create-and-link in one transaction

**Depends on:** Task 12.

**Files:** Modify `internal/store/{assets,services,circuits}.go`, `internal/web/handlers/{assets,services,circuits}.go`, `internal/web/routes.go`. Create `web/templates/partials/project_create_form.html` (one partial, three modes — an asset, a service and a circuit form differ in their fields, not in their framing).

Spec §4 permits a project owner to create an entity "provided it is linked to one of their projects in the same transaction", and forbids linking an entity that already exists. **The mechanism is a project-scoped create route**: the project is a path parameter, so the entity is new by construction and there is nothing for the permit to remember. The map notes create routes take no project field today — there is no existing plumbing, which is why this is three new routes rather than a parameter added to three old ones.

- [ ] **Step 1: Three new routes, and the project is in the URL**

```
POST /projects/{id}/assets/new     -> app.AssetCreateInProject
POST /projects/{id}/services/new   -> app.ServiceCreateInProject
POST /projects/{id}/circuits/new   -> app.CircuitCreateInProject
```

Registered through the existing `write(...)` closure, so they inherit `RequireAuth` + `RequireAdmin` + CSRF unchanged. Note the `/new` suffix: `POST /projects/{id}/assets` already exists and is the **link an existing entity** route, which stays Administrator-only. The two must not collide, and their being adjacent in `routes.go` with a comment explaining the difference is the point.

**Why this shape, written down so it survives.** An earlier revision let a project owner post to `POST /assets` with a project field, and distinguished create-and-link from link-an-existing-entity by having the permit remember ids minted inside the transaction. It worked. It is gone, and the four reasons are the plan's, not a preference:

1. **The same guarantee with no mutable state.** The project is in the URL, so the permit is scoped at mint time and the entity is new by construction of the route. Nothing to record, nothing to reset, nothing to leak across a retry.
2. **It deletes a class of bug rather than testing for it.** `RecordMinted`/`MintedHere`/`ResetMinted`, the transaction-scoped set, the discard-on-rollback rule and the retry test all disappear. A reviewer asked what happens to minted-id state when a `SQLITE_BUSY` retry rebuilds the transaction; with this shape the question cannot be asked, which is strictly better than answering it correctly.
3. **The boundary becomes legible in the routing table.** "A project owner may create inside a project and may not link an existing entity" stops being a runtime property somebody has to reason about and becomes two URLs with two audiences.
4. **It fixes something neither reviewer raised.** With minted-id tracking, `POST /assets` had to be *reachable* by a project owner and then conditionally refused. Now it simply is not theirs, and the existing admin-only gate covers it unchanged — one fewer route where a refusal has to be got right.

**The cost, accepted:** a project-scoped create form, and a create handler doing entity plus link in one transaction. The UI is not a hardship — a project owner already navigates by project, and creating a server from inside the project you are creating it for reads better than creating it loose and linking it afterwards.

- [ ] **Step 2: The store method, and the one carve-out that remains**

```go
func (s *SQLStore) CreateAssetInProject(ctx context.Context, p domain.Permit, projectID string, a *domain.Asset) error
```
plus the service and circuit equivalents. One `writeSerializable` transaction: INSERT the entity, INSERT the link, both audited.

The link row logs `entity_type = "project_asset"` with `entity_id = projectID + "/" + assetID` (`internal/store/projects.go:439,634`). `project_asset` is estate configuration a project owner may not otherwise write. So `Covers` still admits a `project_asset` / `project_service` / `project_circuit` write — but now the condition is simply **that the project half of the composite id is one the permit holds**, which the permit already knows. No memory of the transaction, no question about the entity half, because the entity half cannot be anything the caller chose (Step 3).

That is the whole difference: the carve-out went from "was this id minted in this transaction" — a fact only the transaction knows — to "is this project mine" — a fact the permit was minted with.

- [ ] **Step 3: Creates are INSERT-only and fail on conflict, and the id is server-generated**

**The attack, and it is kept as a test even though the route shape mostly answers it:** pass an *existing* entity id to the create path. A duplicate `code` is refused by the existing unique index, which the `code` variant of this test exercises.

`TestNoCreatePathIsUpsertShaped` — AST over `internal/store/{assets,services,circuits}.go`, asserting no `INSERT` statement in a create method carries `ON CONFLICT` or `OR REPLACE`, with an exact count budget of zero. Reuse `parseSQLWrites`.

## Risks and edge cases

- **The 148-site signature change is the largest diff in this repo's history.** Mitigated by landing it behaviour-neutrally, in the ten enumerated slices, with a `make test` that must pass with zero behavioural test edits. If a behavioural test needs changing, stop and say so.
- **`tx.log` is load-bearing for authorization.** Task 8 is the positive proof and `docs/AUDIT.md` records the fact. This is the plan's largest structural bet and it is stated rather than buried.
- **The minter budget is governance, not security.** Named owner in the comment; `auth-reviewer` required for an addition.
- **Migration safety on a live client database.** `00058` adds two columns with defaults on a 50-100 row table; `00059` creates a new table. Neither rewrites a large table or takes a long lock. Write the down migrations anyway, as goose requires.
- **Role drift on a job change** (spec §5, an accepted cost there). `docs/RECOVERY.md` and the admin docs must repeat it.
- **GDPR.** `change_log.actor` holds an opaque `app_user.id`; role and assignment entries follow it, so the trail carries no personal data and an erasure request is answered by scrubbing the `app_user` row. `user_project` holds a `user_id`, not a name — **and must stay that way.**
- **Narrowing cost visibility is a behaviour change on live deployments.** `CanSeeCosts` returns `CanRead(user)` today, so every authenticated reader currently sees acquisition prices, contract values and project totals. After this, only Administrators and the specifically granted do. **This belongs in the release note and in the upgrade instructions**, not in a support conversation with somebody who lost a screen they had yesterday. Recommend the deployment step explicitly: before upgrading, list who needs the grant; after upgrading, set it.
- **The scrub is new, and the erasure story depended on it existing.** Task 5 Step 4b. Until it lands, `CLAUDE.md`'s erasure argument is not implementable.
- **Data residency.** Nothing leaves the instance; roles are not derived from any external directory (spec §5). No new outbound dependency.
- **No cache on the permit, and no mutable state in it.** A revoked project owner loses access on their next request, and there is no per-transaction state that a rollback or retry could leave behind. The immutability is guarded by `TestThePermitInterfaceCannotBeWidenedWithoutSayingSo` (three methods) and `TestAPermitIsUnchangedByARolledBackTransaction`.

The permit is immutable, `POST /assets` stays Administrator-only and is not a route a project owner has to be conditionally refused on, and the boundary between "create inside a project" and "link an existing entity" is two URLs rather than a runtime property. Task 14 §Step 1 carries the four-point reasoning so it survives the next refactor.
